Dokumendi-mudel

Logist saab JSON-dokument

Klassikaline tekstirida

May 22 19:03:14 web-prod-01
nginx: 10.0.42.7 "GET
/api/orders" 500 142

Ainult grep. Ei tea mis on mis.

JSON-dokument

{
  "@timestamp": "2026-05-22T19:03:14Z",
  "host.name": "web-prod-01",
  "service.name": "nginx",
  "http.response.status_code": 500,
  "event.duration": 234000000
}

Iga väli otsitav, filterdataav, agregeeritav

→ Structured logging. ECS = Elastic Common Schema (de facto standard).

Indeks ≠ SQL "index"

ES-i indeks = dokumentide kollektsioon (nagu SQL tabel).

Monitooringus time-based:

logs-nginx-2026.05.21
logs-nginx-2026.05.22  ← täna kirjutatakse
logs-nginx-2026.05.23
Miks päeva-kaupa?
  • Vana = immutable, optimeerib
  • Kolida odavamale storage'le
  • Kustutada ilma DELETE WHERE
Operatiivsed tööriistad:
  • Index template — schema uutele
  • Alias — atomic rotation
  • Data stream (7.9+) — modern

Klastri arhitektuur
ILM

12:40–13:05 · 25 min

Sõlmerollid — neli rolli

RollMida teebResurssi-profiil
masterKlastri olek, indeksid, shard liigutamineVähe CPU, vaikne
dataHoiab shardide andmeid, indeks + päringPalju mälu, kiired diskid
ingestPipeline'id (grok, geoIP)Palju CPU
coordinatingPäringute routing, koondamineVähe diski

Production: 3 dedicated master + N data + 2+ coordinating-only

Shardid — primary + replica

Indeksi loomisel määrad:

  • number_of_shards (primary) — hilisem muutmine raske
  • number_of_replicas — jooksvalt muudetav

3 primary + 1 replica = 6 shardi kokku

Miks YELLOW single-node klastris?
replicas: 1 → replica peab paiknema erinevas node'is → pole olemas → unassigned → YELLOW

Lisa teine node → replica paigutub → GREEN

Quorum — miks 3 master node'i

Split-brain: võrk lahkneb → 2 master'it korraga → andmed lahknevad.

Lahendus: master valitakse ainult enamuse nõusolekul.

Matemaatika: quorum = ⌊N/2⌋ + 1

NQuorumTalub kadu?
11❌ klaster maas
22❌ quorum kadunud
32✅ üks võib kaduda
53✅ kaks võivad kaduda

Tõsiselt mõeldud klaster = 3 master. Quorum-matemaatika nõuab.

SLA praktikas

SLADowntime/aastasMida nõuab
99.5%43 h1 node, restart OK
99.9%8.7 h3-node, replicas, snapshots S3

Snapshots S3-le = ainus tegelik backup.
Replica ≠ backup. Kustutamine paljundub replicasse. Restore testitud!

ML Anomaly Detection

Unsupervised anomaalia-tuvastus time-series'el.

Mida tuvastab:

Elastic ML = Platinum feature

Plokk 6

Otsing
BM25 · Vector · RAG

14:00–14:15 · 15 min

BM25 = lexical otsing

Inverted index (Lucene) — sõna → dokumendid:

"error"   → [doc1, doc5, doc8]
"timeout" → [doc1, doc12]
"host"    → [doc2, doc5, doc8, doc12]

BM25 skoor sõltub:

  1. Term frequency — palju kordi sõna esineb
  2. Inverse document frequency — kui haruldane sõna
  3. Field length — lühike dokument > pikk

✓ Kiire, täpne, soodne — Kibana Discover vaikimisi

Kus BM25 kukub läbi

Sa otsid: database connection problems

Logides on:

ERROR: DB timeout after 30s
Connection pool exhausted
psycopg2.OperationalError
Lost connection to database server
SQLException: Cannot acquire connection
Ükski ei sisalda sõna "problems". Tihti ei sisalda isegi "database".
Vocabulary mismatch — sinu sõnastik ≠ logi-rea sõnastik.

Lahendus: vector search — võrdleb tähendusi, mitte sõnu

Vector search + HNSW

Embedding mudel (ELSER, e5, OpenAI, Cohere):

"DB timeout"       → [0.91, 0.12, 0.04, ...]
"connection pool"  → [0.89, 0.15, 0.06, ...]
"OperationalError" → [0.87, 0.14, 0.08, ...]

Sarnased tähendused → vektorid lähedal cosine-ruumis.

HNSW (Hierarchical Navigable Small World) — graaf, ~5ms päring 1M vektoris (mitte 500ms brute-force).

⚠️ Kompromiss: RAM-kallis. Heap 2× logide-klastri kohta.

🎯 Cheat sheet ② — Klastri sizing

99.5%   → 1 node, restart OK
99.9%   → 3 master + N data, replicas=1, snapshots S3
99.99%  → 3 master + N data ÜLE 3 AZ-i + standby
99.999% → Multi-region + CCR (harva)

Checklist enne tootmist:

  • ☐ 3 dedicated master node'i
  • ☐ heap = ½ RAM-ist, max 31 GB
  • ☐ number_of_replicas ≥ 1
  • ☐ Snapshot S3-le + restore testitud
  • ☐ ILM policy hot → warm → cold → frozen → delete
  • ☐ Kafka buffer kui > 100 GB/päev
